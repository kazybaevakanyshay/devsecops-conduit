# Lesson 08 · Compose: the whole application in one file, released by the robot

By the end of the lesson:

- one Compose file describes everything that runs, and one command starts it;
- PostgreSQL runs in a container, with all your old data;
- the containers have their own network, and only the port Caddy needs is published;
- the robot releases containers again; you rolled a bad release back by re-running it and repaired `main` with a revert.

You work on the laptop, in `~/devsecops-conduit`, and on your server, where Conduit runs from two containers since Lesson 7. In the commands, replace `YOUR-IP` with the address of your server and `<you>` with your GitHub username **in lower case**.

## Starting state

- `sudo docker ps` on the server shows `conduit-api` and `conduit-web`, started from the robot's images `ghcr.io/<you>/…` (Lesson 7, Mission 5).
- Your fork's `ci.yml` has the job `build-images`, and the `deploy` job is paused with `if: false` (Lesson 7, Mission 4).
- Your two packages on GitHub are public.

## Mission 1 · One file instead of two commands (30 minutes)

**1. Install Compose on the server:**

```bash
ssh azureuser@YOUR-IP
sudo apt update
sudo apt install -y docker-compose-v2
sudo docker compose version
```

Checkpoint: `Docker Compose version 2.…`.

**2. Find the version that runs now.** Still on the server:

```bash
sudo docker ps --format '{{.Names}} {{.Image}}'
```

The part after `:` is a commit SHA. Copy it; you need it in step 5.

**3. A branch on the laptop:**

```bash
cd ~/devsecops-conduit
git switch main
git pull
git switch -c compose/release
```

**4. Write the two commands as one file.** Create `deploy/compose.yaml`:

```yaml
name: conduit

services:
  api:
    image: ghcr.io/<you>/conduit-api:${TAG}
    network_mode: host
    env_file: /etc/conduit/conduit.env
    environment:
      UVICORN_HOST: 127.0.0.1
    restart: unless-stopped

  web:
    image: ghcr.io/<you>/conduit-web:${TAG}
    network_mode: host
    env_file: /etc/conduit/web.env
    restart: unless-stopped
```

Put it next to last week's homework: every flag of `docker run` became one line. `--name` became the service name, `--network host` became `network_mode`, `--env-file` became `env_file`, `-e` became `environment`, `--restart` stayed `restart`. The SHA is no longer in the file: `${TAG}` is filled in from a second file, in the next step.

```bash
git add deploy/compose.yaml
git commit -m "Describe both containers in one Compose file"
git push -u origin compose/release
scp deploy/compose.yaml azureuser@YOUR-IP:/tmp/compose.yaml
```

**5. Put the file in place and choose the version.** On the server, with the SHA from step 2:

```bash
sudo cp /tmp/compose.yaml /opt/conduit/compose.yaml
echo "TAG=<the SHA>" | sudo tee /opt/conduit/.env
cd /opt/conduit
```

> [!NOTE]
> Compose reads the file `.env` in the same folder and puts its values into `${…}`. The description of the application stays the same from release to release; only one line, `TAG=…`, changes. To know what runs on a server, read that one line.

**6. Replace the two containers with the file:**

```bash
sudo docker rm -f conduit-api conduit-web
sudo docker compose up -d
sudo docker compose ps
curl -s localhost:8000/api/health-check
```

Checkpoint: `conduit-api-1` and `conduit-web-1` are `Up`, the health check shows your SHA, and `https://YOUR-NAME` works.

**7. Run it once more:**

```bash
sudo docker compose up -d
```

Checkpoint: both lines say `Running`. Nothing was started again.

> [!NOTE]
> The file describes how the server should look. Compose compares it with what runs and changes only what differs, exactly like `changed=0` from the playbook in Lesson 5. Change one line in the file, and only that container is created again.

> [!WARNING]
> `docker compose config` prints the complete file with every value filled in, including the passwords from `/etc/conduit`. Do not run it on a projector and never paste its output anywhere.

## Mission 2 · The database moves in (50 minutes)

**1. Describe the whole application.** On the laptop, replace `deploy/compose.yaml` with:

```yaml
name: conduit

services:
  db:
    image: postgres:16
    env_file: /etc/conduit/conduit.env
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U conduit -d conduit"]
      interval: 5s
      retries: 10
    restart: unless-stopped

  api:
    image: ghcr.io/<you>/conduit-api:${TAG}
    env_file: /etc/conduit/conduit.env
    environment:
      POSTGRES_HOST: db
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      interval: 10s
      retries: 6
      start_period: 30s
      start_interval: 2s
    restart: unless-stopped

  web:
    image: ghcr.io/<you>/conduit-web:${TAG}
    env_file: /etc/conduit/web.env
    environment:
      REACT_PUBLIC_API_ENDPOINT: http://api:8000/api
    ports:
      - "127.0.0.1:3000:3000"
    depends_on:
      api:
        condition: service_healthy
    restart: unless-stopped

volumes:
  pgdata:
```

Read it line by line:

- `db` is the official PostgreSQL image. On its very first start it creates the user, the password and the database from `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB`. Those names are already in `/etc/conduit/conduit.env` since Lesson 3.
- `pgdata` is a volume. The database files live there, not inside the container.
- `network_mode: host` is gone. Compose creates a private network for the three boxes, and each box finds the others by service name: the API connects to `db`, the frontend to `api`. A value under `environment` wins over the same name in `env_file`.
- Only `web` publishes a port, and only on `127.0.0.1`, for Caddy. The database and the API cannot be reached from outside their network.
- `healthcheck` and `depends_on` decide the order: first the database is healthy, then the API, then the frontend starts.

```bash
git add deploy/compose.yaml
git commit -m "Move the database into a box and give the boxes their own network"
git push
scp deploy/compose.yaml azureuser@YOUR-IP:/tmp/compose.yaml
```

**2. Count what you have.** On the server:

```bash
sudo -u postgres psql -d conduit -tAc 'select count(*) from article'
```

Write the number down.

**3. A short break for the site, then an empty database in a box:**

```bash
cd /opt/conduit
sudo cp /tmp/compose.yaml compose.yaml
sudo docker compose stop api web
sudo docker compose up -d db
sudo docker compose ps db
```

Repeat the last command until it says `healthy`. Your site is down now. Companies call this a maintenance window and keep it short.

**4. Move the data** from the old database into the box:

```bash
sudo -u postgres pg_dump --no-owner --no-privileges conduit \
  | sudo docker compose exec -T db psql -U conduit -d conduit -q -v ON_ERROR_STOP=1 > /dev/null
sudo docker compose exec db psql -U conduit -d conduit -tAc 'select count(*) from article'
```

`pg_dump` writes the whole database as SQL text; the pipe `|` hands that text to `psql` inside the box. Checkpoint: the same number as in step 2.

**5. Start the rest:**

```bash
sudo docker compose up -d
sudo docker compose ps
```

Checkpoint: three containers. `db` and `api` are `healthy`, `web` is `Up` with `127.0.0.1:3000->3000/tcp`. Open `https://YOUR-NAME`: your articles are there.

**6. Switch the old database off for good**, and look at the open doors:

```bash
sudo systemctl disable --now postgresql
sudo ss -tlnp
```

Checkpoint: nothing listens on `5432` or `8000` any more. `3000` is open only on `127.0.0.1`.

> [!WARNING]
> Docker writes its own firewall rules for published ports, and they skip the firewall of the server. `"3000:3000"` would open the frontend to the whole internet; only the firewall in Azure would stand in the way. `"127.0.0.1:3000:3000"` opens it only on the server itself, where Caddy is.

**7. Sign in.** Open `https://YOUR-NAME` and sign in. It fails: `Oops! An unexpected error occurred.` Read the logs before you guess:

```bash
sudo docker compose logs web | tail -20
```

Checkpoint: a line `POST /login.data 400` and above it `Error: Bad Request`.

> [!NOTE]
> Before it accepts a form, the frontend checks that the form came from its own site. That stops other websites from submitting forms in your name. To see the real address, it reads the `X-Forwarded-*` headers that Caddy adds, but it believes them only from a proxy it trusts. Since Lesson 4 that was `loopback`: Caddy on the same machine. Now Caddy's requests reach the box through Docker's private network, from an address like `172.18.0.1`, so the frontend ignores the headers and refuses the form.

**8. Trust the private network too.** On the laptop, in `frontend/server.js`, change the two lines

```js
// A reverse proxy on this machine (Caddy) is in front of us: believe its X-Forwarded-* headers.
app.set("trust proxy", "loopback");
```

to

```js
// Caddy is in front of us, on this machine or across Docker's private network: believe its X-Forwarded-* headers.
app.set("trust proxy", "loopback, uniquelocal");
```

```bash
git add frontend/server.js
git commit -m "Trust Caddy across Docker's private network"
git push
```

The fix is in Git, but the server runs an image. A new image comes from the robot, in Mission 3. Until then, reading works and signing in does not.

> [!NOTE]
> `uniquelocal` means private addresses such as `10.…`, `172.16.…` to `172.31.…` and `192.168.…`. A public address is still not believed, because anyone on the internet can write `X-Forwarded-Proto: https` into a request. Port `3000` is published only on `127.0.0.1`, so the only ones who can reach the frontend are Caddy and the boxes.

**9. Prove that the data stays:**

```bash
sudo docker compose down
sudo docker volume ls
sudo docker compose up -d --wait
sudo docker compose exec db psql -U conduit -d conduit -tAc 'select count(*) from article'
```

Checkpoint: after `down` all containers and the network are gone, the volume `conduit_pgdata` is still listed, and after `up` the number of articles is the same.

> [!WARNING]
> `sudo docker compose down -v` also removes the volumes, and with them every user and article. There is no undo. Never type it on a server whose data you need.

## Mission 3 · The robot is back (35 minutes)

**1. A playbook for containers.** On the laptop, replace `deploy/playbook.yml` with:

```yaml
- name: Release one commit as containers
  hosts: conduit
  become: true

  tasks:
    # ---- what the server needs: Docker and a web server ----
    - name: Install Docker, Compose and the web server
      ansible.builtin.apt:
        name: [docker.io, docker-compose-v2, caddy]
        update_cache: true
        cache_valid_time: 3600

    # ---- the secrets stay on the server, as before ----
    - name: Create the folder for the secrets
      ansible.builtin.file:
        path: /etc/conduit
        state: directory
        mode: "0700"

    - name: Create the API secrets once and never overwrite them
      ansible.builtin.copy:
        dest: /etc/conduit/conduit.env
        force: false
        mode: "0600"
        content: |
          APP_ENV=prod
          SECRET_KEY={{ lookup('ansible.builtin.password', '/dev/null', length=48, chars=['ascii_letters', 'digits']) }}
          JWT_SECRET_KEY={{ lookup('ansible.builtin.password', '/dev/null', length=48, chars=['ascii_letters', 'digits']) }}
          POSTGRES_HOST=127.0.0.1
          POSTGRES_PORT=5432
          POSTGRES_DB=conduit
          POSTGRES_USER=conduit
          POSTGRES_PASSWORD={{ lookup('ansible.builtin.password', '/dev/null', length=32, chars=['ascii_letters', 'digits']) }}
      no_log: true

    - name: Create the frontend secrets once and never overwrite them
      ansible.builtin.copy:
        dest: /etc/conduit/web.env
        force: false
        mode: "0600"
        content: |
          PORT=3000
          REACT_PUBLIC_API_ENDPOINT=http://127.0.0.1:8000/api
          SESSION_SECRET={{ lookup('ansible.builtin.password', '/dev/null', length=48, chars=['ascii_letters', 'digits']) }}
      no_log: true

    # ---- the release: one file and one version number ----
    - name: Create the folder of the application
      ansible.builtin.file:
        path: /opt/conduit
        state: directory
        mode: "0755"

    - name: Describe the containers
      ansible.builtin.copy:
        src: compose.yaml
        dest: /opt/conduit/compose.yaml
        mode: "0644"

    - name: Choose the version to run
      ansible.builtin.copy:
        dest: /opt/conduit/.env
        content: "TAG={{ revision }}\n"
        mode: "0644"

    - name: Download the images of this version
      ansible.builtin.command: docker compose pull
      args:
        chdir: /opt/conduit
      changed_when: false

    - name: Start this version and wait until it is healthy
      ansible.builtin.command: docker compose up -d --wait --wait-timeout 180
      args:
        chdir: /opt/conduit
      register: up
      changed_when: "'Start' in up.stderr"

    # ---- the web server in front, as in Lesson 4 ----
    - name: Configure the web server
      ansible.builtin.template:
        src: Caddyfile.j2
        dest: /etc/caddy/Caddyfile
        mode: "0644"
      notify: Reload the web server

    - name: Start the web server now and after every reboot
      ansible.builtin.systemd_service:
        name: caddy
        state: started
        enabled: true

    - name: Apply the web server change now
      ansible.builtin.meta: flush_handlers

    # ---- the check ----
    - name: Check that the frontend answers
      ansible.builtin.uri:
        url: http://127.0.0.1:3000/
      register: page
      retries: 30
      delay: 1
      until: page.status == 200

    - name: Ask the API which version runs
      ansible.builtin.command: docker compose exec -T api curl -fs http://127.0.0.1:8000/api/health-check
      args:
        chdir: /opt/conduit
      register: health
      changed_when: false

    - name: Show the running version
      ansible.builtin.debug:
        msg: "{{ health.stdout }}"

  handlers:
    - name: Reload the web server
      ansible.builtin.systemd_service:
        name: caddy
        state: reloaded
```

Read it task by task. Gone: Node.js, `pip`, `npm`, the Git checkout, the systemd units and the tasks that created the database user: the database box creates its user itself. Kept: the secrets, created once on the server and never overwritten. New: copy `compose.yaml`, write the version into `.env`, download the images, start them and wait until they are healthy. If the API never becomes healthy, `--wait` fails and the robot turns red.

**2. Delete what nobody uses:**

```bash
git rm deploy/conduit.service.j2 deploy/conduit-web.service.j2
```

In `deploy/inventory.ini` delete the line that starts with `repo_url=`: the server never downloads code again.

**3. Wake the robot up.** In `.github/workflows/ci.yml`, change the top of the `deploy` job to:

```yaml
  deploy:
    needs: [build-images]
    if: github.event_name == 'push'
```

and its step `Install Ansible` to:

```yaml
      - name: Install Ansible
        run: pip install ansible-core
```

`deploy` now waits for `build-images`, which waits for the two checks. Without images there is nothing to release.

**4. Commit, push, open a pull request into your own fork, merge it:**

```bash
git add deploy/playbook.yml deploy/inventory.ini .github/workflows/ci.yml
git commit -m "Release containers with Compose; the robot is back"
git push
```

The pull request has four commits: the two Compose files, the sign-in fix and the robot.

**5. Watch the robot.** On `main`: `unit-tests` and `secret-scan`, then `build-images` (about a minute), then `deploy` (about two minutes). Open the log of `deploy` and find the task `Start this version and wait until it is healthy`.

Checkpoint, on the laptop:

```bash
git switch main
git pull
git rev-parse HEAD
ssh azureuser@YOUR-IP cat /opt/conduit/.env
```

`TAG=` is the same SHA. Now sign in on `https://YOUR-NAME`: it works. The fix reached the server the only way it can now: in an image the robot built.

> [!NOTE]
> In Lesson 5 the playbook installed Python, Node, libraries and services, and built the frontend on the server. Now everything is inside the images, built once by the robot. A release is two facts: this `compose.yaml` and this `TAG`.

## Mission 4 · A bad release, a quick way back (25 minutes)

**1. The same typo as in Lesson 6.** On a new branch, in `backend/conduit/api/routes/health_check.py`, change the last line from `return response` to `return respons`.

```bash
git switch -c release/tidy-health
python -m pytest tests/unit -q
git add backend/conduit/api/routes/health_check.py
git commit -m "Tidy the health check"
git push -u origin release/tidy-health
```

Open the pull request: two green checks. Merge it.

**2. Watch the robot refuse.** `build-images` is green: the image builds fine. About two minutes later `deploy` turns red at `Start this version and wait until it is healthy`, with `dependency failed to start: container conduit-api-1 is unhealthy`. Open `https://YOUR-NAME`: `502 Bad Gateway`. On the server:

```bash
cd /opt/conduit
sudo docker compose ps
```

Checkpoint: `api` is `unhealthy`, and `web` is not in the list at all. Your site is down.

> [!NOTE]
> The release first replaced the boxes and only then checked them. The new frontend waits for a healthy API (`depends_on`), so it never started. Big companies start the new version next to the old one and send users to it only once it is healthy; we have one server and one copy, so a bad release means downtime until somebody rolls back.

**3. Roll back, and time it.** In the **Actions** tab open the last green run on `main`, the merge of `compose/release`. Next to the job `deploy`, click the round arrow (**Re-run job**) and confirm. Note the time.

Checkpoint: in under two minutes the job is green, `https://YOUR-NAME` works again, `cat /opt/conduit/.env` shows the earlier SHA, and `sudo docker compose ps` shows `api` `healthy`. Write the time on the board next to Lesson 6.

> [!NOTE]
> The earlier run already tested its commit and built its images. Running `build-images` again would only build the same thing twice. Re-running `deploy` writes the old `TAG` and starts images that are already on the server: nothing is built and nothing is downloaded. Open the log: the task `Start this version and wait until it is healthy` takes about ten seconds. The rest of the time is the robot's machine starting and Ansible checking every other task of the playbook.

**4. Repair `main`.** Open the merged pull request `release/tidy-health` and click **Revert**, then merge the new pull request. Checkpoint: `deploy` on `main` is green and `TAG=` is the newest SHA.

## Troubleshooting

1. **`unknown command: docker compose`.** Compose is not installed: `sudo apt install -y docker-compose-v2`.
2. **`no configuration file provided: not found`.** You are not in `/opt/conduit`. `cd /opt/conduit` first.
3. **`The "TAG" variable is not set`, then `invalid reference format`.** `/opt/conduit/.env` is missing or empty. Repeat Mission 1, step 5.
4. **`manifest unknown` when the images are pulled.** There is no image for that SHA. Use the full SHA of a commit on `main` whose `build-images` job is green.
5. **`address already in use` on `up`.** A container from Lesson 7 still runs: `sudo docker rm -f conduit-api conduit-web`.
6. **The restore prints `relation … already exists`.** The API box started on the empty database before the data moved in and created empty tables. Only if the old database is still running: `sudo docker compose down`, `sudo docker volume rm conduit_pgdata`, and repeat Mission 2 from step 3.
7. **The articles are gone after Mission 2.** The box started with a new, empty volume. The old database is switched off, not deleted: `sudo systemctl start postgresql`, then repeat Mission 2 from step 3.
8. **Sign-in shows `Oops! An unexpected error occurred.`** The fix from Mission 2, step 8, is not on the server yet. It arrives with the robot's next release (Mission 3).
9. **`deploy` fails with `container conduit-api-1 is unhealthy`.** The API does not answer its health check. `sudo docker compose logs api` shows why.
10. **`deploy` fails with `Permission denied (publickey)` or `Host key verification failed`.** The robot's key or `deploy/known_hosts` from Lessons 5 and 6 is missing; see the troubleshooting of Lesson 6.
11. **The site shows `502 Bad Gateway`.** Caddy cannot reach the frontend. `sudo docker compose ps` must show `127.0.0.1:3000->3000/tcp` next to `web`. If `web` is missing after a red release, the API is unhealthy: roll back (Mission 4, step 3).

## Commands for today

| Goal | Command, in `/opt/conduit` |
|---|---|
| Make the server look like the file | `sudo docker compose up -d` |
| The same, and wait until healthy | `sudo docker compose up -d --wait` |
| What runs? | `sudo docker compose ps` |
| Logs of one service | `sudo docker compose logs web` |
| A command inside a service | `sudo docker compose exec api <command>` |
| Start only one service | `sudo docker compose up -d db` |
